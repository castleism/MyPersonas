# MyPersonas AI content provenance and watermark contract

Status: **forward-only migration 060 is applied and read back in the linked production
database; matching function/frontend deployment and live integration verification remain
separate gates.** Migration 059 is immutable historical source and must not be edited or
re-run to add the missing hardening. The complete contract below is the coordinated 059
baseline plus the 060 hardening release.

Exact package hashes, verification evidence, approval gates, and release order are in
`RELEASE-MANIFEST-2026-08-23-AI-PROVENANCE.md`.

## User-visible rule

Every file uploaded through a MyPersonas media picker requires one declaration:

- **No AI** — generative AI was not used. The exact source bytes are retained as the
  public file and their source and content SHA-256 values must match.
- **AI-assisted** — AI materially edited, extended, or helped create the asset.
- **AI-generated** — the asset was primarily generated by AI.
- **Not sure** — the owner cannot reliably determine whether AI was used.

The last three choices receive the same visible MyPersonas AI mark. Choosing “Not
sure” never silently becomes “No AI.” The declaration UI can be cancelled, but it
cannot be skipped. This is an owner declaration, not an automated truth detector.

Images generated by the site are always classified `generated`; the browser cannot
downgrade that classification. The generation service records a short-lived event
containing the owner, persona, backend, provider, model, prompt hash, output hash, MIME
type, and expiry, submits the source directly to the trusted media service, and returns
only the registered, server-watermarked public URL. Raw generated pixels are never sent
to the browser as a data URL.

## Image treatment

The exact owner-supplied master is:

`assets/MyPersonas-AI-Watermark.png`

- SHA-256: `c8ff9543374ab294ebf73ce0859581abf5e12251b7ce2735d86399d015e046b2`
- Source dimensions: 2172 × 724 RGBA PNG
- Visible source crop: x 345, y 204, width 1481, height 306
- Standard position: bottom right
- Mark opacity: 22%; dark halo opacity: 10%
- Margin: 2.5% of the shorter image side, clamped to 8–48 pixels
- Width: approximately 24% of the image, bounded for readability and image height

For an ordinary image, the mark is burned into the final PNG, JPEG, or WebP bytes and
the public derivative is proportionally reduced when needed to remain at or below the
two-megapixel worker output ceiling.
For Facebook, Instagram, and X composer media, each platform crop is made first and
then independently watermarked. This prevents a later cover crop from removing the
mark. Album displays use `object-fit: contain` for declared AI images, while the full
owner preview always shows the whole canonical derivative and downloads that same file.
Cover-cropped avatar, banner, page-background, relationship, and reel views also carry
an asset-level accessible disclosure so CSS presentation cannot hide the only visible
signal.

The master PNG contains a `caBX` C2PA/JUMBF container whose payload identifies trained
algorithmic media. The repository preserves that exact master, but this local review did
not cryptographically verify its signer. Browser canvas encoding does not preserve a
source file's C2PA manifest, so generated derivatives must not be described as C2PA-
signed. Their authority is the MyPersonas database provenance record plus exact hashes.

## Non-static assets

The current canonical intake supports PNG, JPEG, WebP, GIF, MP4, and WebM byte
validation. AI-used GIFs, APNGs, animated WebPs, and videos intentionally fail closed: a
single CSS overlay or first-frame mark would disappear when the file is downloaded or
reposted. They remain blocked until a server worker can decode, mark every frame,
re-encode, and validate the final bytes. No-AI GIF/video uploads retain their exact
bytes.

Future audio and document intake should use the same required declaration and immutable
registry. Because an audible watermark would alter the work, AI-used audio should carry
a persistent visible player/download badge plus signed metadata. Documents should place
the mark on every rendered page and retain a visible download disclosure. Those paths
are roadmap work, not a claim about this release.

## Security and data flow

```text
owner file -> required declaration -> source SHA-256
           -> authenticated media-ingest Edge Function receives raw source
           -> JWT + origin + persona ownership + hash + size + header validation
           -> safe decode; optional social crop; verify bundled master SHA-256
           -> server creates final raster and burns the mark when AI use != none
           -> service-only immutable Storage write
           -> service-authored persona_media_assets provenance row
           -> exact asset ID bound to profile/post/album/draft consumer
           -> page review and social approval verify current provenance hash
```

Important boundaries:

- The browser helper can render a local preview, but the service never accepts that
  preview as watermark proof. Only server-created final bytes can receive
  `watermark_state=system_applied`.
- MIME type is detected from file bytes. Extension and browser header are not trusted.
- AI-used sources are capped at 5 MiB and 12 megapixels in the Edge worker. All marked
  outputs are capped at 2 megapixels and 10 MiB. Static no-AI PNG/JPEG/WebP files also
  receive header/dimension validation. These are compressed-byte and pixel safety bounds,
  not a promise that every pathological file will fit hosted CPU/memory limits.
- Canonical paths include owner, declaration, source, persona ID, purpose, and final
  content hash, so identical owner bytes cannot collide between personas.
- New canonical or local URLs fail if their active provenance row is absent. AI-used
  Supabase render URLs are rejected because a transform could crop away the mark. A
  bounded no-AI transform is allowed. External HTTPS media present at the first successful
  060 hardening apply is snapshotted once, remains visibly labeled “AI use not known,” and must be
  re-ingested when changed. New external or local media references make publication
  incomplete; neither 059 nor 060 invents historical declarations.
- Provenance fields and hashes are immutable. Corrections require a new derivative.
- A generated asset also requires a matching unexpired server generation event. Event
  consumption and provenance-row insertion occur in one database transaction.
- Social approval freezes the exact Facebook/Instagram provenance hashes and rejects
  changed or missing authority during scheduling/publishing.
- Archiving or flagging an asset requires AAL2 and invalidates the affected persona's
  published/review revision. Archived public objects continue to count. The service
  registry enforces 200 new assets per owner per UTC day, 2 GiB and 5,000 retained
  records per owner, plus 512 MiB and 1,000 retained records per persona.
- Public Storage URLs still contain a stable owner UUID and can correlate otherwise
  separate personas. Opaque public delivery remains a separate release blocker.

## Coordinated release order

Use a maintenance window because the coordinated hardening removes direct browser Storage
writes. The safe order is:

1. Inventory and back up the linked schema, policies, functions, bucket configuration,
   migration ledger, and existing media records. Confirm migrations through 058, the exact
   051 manifest, and the existing 059 ledger row. Do not replace or re-run 059.
2. Pause media writes and scheduled publishers. In a matching isolated database, rehearse
   prerequisite seed → frozen 059 → 060 → 060 reapply → adversarial runtime assertions.
3. Apply and read back **migration 060 only** in the linked project.
4. Deploy and verify `media-ingest`, `gemini-image`, `compose-post`, and `ai-proxy`
   together with the
   other publisher functions that consume `post_drafts`. Use local Supabase CLI bundling:
   the pinned ImageMagick WASM exceeds the server-side dashboard bundle limit, and the
   watermark PNG must be included through `static_files`.
5. Deploy the matching static assets, clear/version caches, and run signed-in upload,
   generation, page review, social approval, public display, download, desktop, and mobile
   tests using separate owner and other-owner accounts.
6. Resume publishers only after exact provenance survives approval and reconciliation.

If any phase fails, keep media writes and publishing paused. Do not restore the old
browser-write policy as a convenience rollback; that would reopen the authority bypass
the migration is designed to close.

## Next recommendations

1. Build an isolated media-transcode worker for frame-by-frame GIF/video marking, with
   codec limits, decompression-bomb defenses, timeouts, malware scanning, and exact-output
   hashes before enabling AI-used motion media.
2. Add a server-side C2PA signing service for final derivatives only after key custody,
   certificate rotation, verification, and recovery procedures are approved.
3. Replace stable owner UUIDs in public media URLs with opaque public asset identifiers.
   Until that migration and backfill are verified, keep rich public image/video widgets
   and video backgrounds disabled; 060 does not resolve this privacy blocker.
4. Add private retention for original upload evidence only if there is a clear consent,
   deletion, access-control, cost, and legal purpose; source hashes alone are the current
   minimal-data design.
5. Add moderation and dispute workflows for knowingly false declarations without using
   unreliable AI detectors as automatic proof.
6. Add a declared import-by-URL workflow so newly supplied external media can be fetched
   safely, license-confirmed, scanned, declared, and—where permitted—securely rehosted
   instead of remaining blocked by the publication gate.
